# RFC 0001: 核心边界与领域基础

状态: 讨论中. 本文仅记录访谈中已确认的基础决策, 不是完整架构或工程 SPEC.

## 已确认决策

### Q1: Effect Runtime 不承担计算恢复

核心负责独立 Effect 的持久化、执行尝试管理、结果接受与查询. 第一阶段不负责持久化 Workflow 依赖图, 也不恢复 Agent 控制流.
Agent 上下文及等待关联的必要持久化由上层负责.

理由: 保持 Effect-level Recovery 与 Computation Recovery 的边界清晰, 避免为支持 Agent 场景而隐式发展成完整 Workflow
Engine.

未采用的替代方案: 将 Agent 状态、依赖图与计算恢复统一纳入核心. 代价: Beamlet 单独不能承诺完整 Agent Recovery;
上层需要保存足够上下文以定位相关 Intent.

### Q2: 每个 Intent 只有一个逻辑 Authority

Outcome 接受与关键生命周期变化由该 Intent 的唯一逻辑 Authority 裁决. 此约束不要求全系统中心化, 不要求单个 Coordinator
进程, 也不要求不同 Intent 共享同一 Authority.

理由: 将 Outcome 的权威唯一性与多 Worker 执行并发分开, 避免分区期间出现互相冲突的权威终态.

未采用的替代方案: 不可达时自动在其他节点建立独立权威结果, 或允许双边接受后再合并. 代价: 缺少安全迁移协议时, Authority
不可用会影响权威提交的可用性.

补充需求: 现有权威节点停用时支持手动迁移. 第一阶段范围已在 Q6 确认为旧 Authority 可配合的计划迁移,
具体撤权与交接协议尚未确定.

### Q3: 不确定执行不自动授权危险重试

超时、lease 到期或 Worker 失联本身不足以授权重新执行可能产生不可重复副作用的操作.
自动重试需要可靠的外部幂等协议、能够确认未执行的查询结果, 或调用方明确接受重复等依据; 无依据时保留不确定性并协调处理.

理由: 外部操作可能已成功, 但内部尚未记录结果. 拒绝旧 Worker 提交也不能阻止其在不验证权限的外部服务上产生副作用.

未采用的替代方案: 将超时统一解释为未执行或失败, 再无条件重新调度. 代价: 某些 Intent 需要外部查询或人工处理,
无法承诺自动完成.

### Q4: 显式稳定提交身份

调用方可提供作用域内稳定的 Submission Key. 相同 key 与相同不可变定义对应已有 Intent, 冲突定义应拒绝而非覆盖; 无 key
的新提交表示新的逻辑操作. 同一 key 的并发提交需要具有原子 create-or-get 语义, 具体实现尚未确定.

理由: 相同输入不代表同一操作, 但恢复后的同一逻辑请求需要重新定位原 Intent.

未采用的替代方案: 默认按输入 hash 去重, 或要求调用方自行通过输入搜索已有结果. Submission Key 与外部 Idempotency Key
不等价. 作用域、定义相等规则及保留期限待定.

### Q5: 采用 IEO 作为领域起点

采用 [Intent / Execution / Outcome](../../GLOSSARY.md) 作为领域语言. Execution 建立不表示外部操作已开始,
可以保留未被接受为 Outcome 的结果证据. Outcome 是不可变权威结果, 每个 Intent 至多一个.

理由: 将逻辑操作、执行尝试与权威接受分开, 可以描述重复执行、迟到报告及结果复用, 不将内部提交语义混同于外部副作用语义.

未采用的替代方案: 先用通用状态机实体替代领域概念. 表数量、Execution 状态枚举或通用 Transition 框架尚未决定; Intent
生命周期见 Q21, 合格终结候选的竞争规则见 Q18. Outcome 至多一个是 safety 要求, 不证明最终一定产生 Outcome.

### Q6: 第一阶段支持计划手动迁移

支持旧 Authority 可配合的计划手动迁移, 用于节点停用或更换设备; 不承诺旧 Authority 不可达时的强制接管,
也不承诺无停机迁移.

理由: 用允许安全暂停的交接满足正常退役需求, 不将分区接管、备份恢复与正常迁移混成一个协议.
迁移需要分别保证一致的数据切点、旧 Authority 撤权和新 Authority 激活; 一致备份或目标库 epoch 增加不能独自满足这些条件.

未采用的替代方案: 第一阶段同时支持透明故障接管及无停机迁移. 代价: 强制接管需另行定义旧副本隔离、数据丢失和外部授权假设,
计划迁移也可能暂停服务. 在途操作与回调交接、迁移中断恢复仍待设计.

### Q7: Unknown 不是终态 Outcome

执行结果未知表示操作尚未解决, 本身不产生终态 Outcome. Intent 保持未解决, 可以根据迟到报告、外部查询或人工协调继续处理.

理由: 外部操作可能已发生, 后续证据可以消除不确定性; 不能提前提交不可变失败结果来替代未知事实.

未采用的替代方案: 超时或失联直接提交 Unknown/Failed 终态, 然后原地修正 Outcome.
状态字段或独立证据字段的表达方式尚未决定.

### Q8: 单次失败不自动终结 Intent

Execution 报告失败不自动产生 Intent 的失败 Outcome. 尝试失败事实应保留; Intent
是否继续或最终失败需要明确策略和终结提交规则.

理由: 一次尝试结束与逻辑操作结束是不同事实, 允许在满足 Q3 安全条件时再次尝试.

未采用的替代方案: 任一次 Execution 失败就使 Intent 失败. 本决策也不意味着所有失败都可重试; 失败分类、预算和终结规则待定.

### Q9: 核心采用统一异步提交语义

所有 Effect 先持久化接受 Intent, 再异步处理, 最后查询或等待 Outcome. 同步等待可以作为调用侧便利接口, 等待进程退出不改变
Intent 身份或生命周期. 长等待不应要求 Worker 进程始终存活.

理由: 保持提交、执行和等待三个环节独立, 避免调用进程成为操作恢复的必要条件.

未采用的替代方案: 按同步/异步划分两类 Intent. 统一核心语义不要求统一所有 Handler 的执行协议;
立即返回、挂起等待与外部回调的协议待定.

### Q10: 审计覆盖重要的无状态变化事实

审计不仅包含成功状态转换, 也包含重要的迟到报告、提交拒绝和冲突事实. 不要求记录每次轮询或心跳.

理由: 拒绝旧 Worker 的成功报告可能不改变当前状态, 却是解释副作用、提交竞态和恢复过程的重要证据.

未采用的替代方案: 审计仅记录 from/to 改变, 或将所有普通日志都写入领域历史. 此决策不引入 Event Sourcing;
记录实体、去重、原子提交及保留策略尚未确定.

### Q11: 取消是逻辑终结, 不证明外部停止

区分请求 Handler 停止执行与 Authority 接受取消 Outcome. 取消 Outcome 提交后不再授权新的 Execution, 也不再接受另一个
Outcome; 可以尝试停止在途操作, 但不承诺其已停止或回滚. 迟到的执行事实仍可保留.

理由: 外部操作可能在取消提交前后继续产生副作用, Runtime 的逻辑终结不能替代外部停止证据.

未采用的替代方案: 取消等同外部操作已停止/撤销, 或取消请求本身自动获胜. 取消与完成提交的竞态规则见 Q18, Handler
停止请求的执行协议尚未确定.

### Q12: 明确撤权的 Execution 不可直接赢得提交

某个 Execution 的提交资格被明确撤销后, 即使它报告成功且 Intent 尚无 Outcome, 也不能直接提交为 Outcome.
其报告可以作为证据保存, 由有资格的 Authority 通过明确的 reconciliation 流程验证和使用.

理由: 报告接收与权威提交资格不同, 不能允许先返回的旧尝试绕过撤权.

未采用的替代方案: 只要 Outcome 尚未存在, 任何尝试的成功报告均可直接获胜; 或将已撤权尝试的报告一律丢弃. lease 与
Execution 结果接受资格分离的原则见 Q19, 具体验证守卫仍待定义.

### Q13: 第一阶段不做主动 hedging

同一 Intent 默认只保留一个当前被授权执行的尝试, 第一阶段暂不提供为抢延迟而同时授权多个尝试的主动 hedging. 不同 Intent
可以并发执行, 数据模型仍保留多个 Execution 的独立记录.

理由: 降低提交竞争与外部重复操作的策略复杂度, 不提前引入竞速获胜规则.

未采用的替代方案: 第一阶段默认主动竞速执行. 旧尝试被撤权不证明其外部执行已停止,
因此授权唯一性不能等同于真实外部执行互斥; 替代尝试仍须符合 Q3.

### Q14: Handler 可采用持久化 Pending 协议

Handler 可以报告完成结果, 也可以报告进入可恢复等待. Runtime 保存必要等待身份与关联后可释放执行进程,
恢复时通过回调或外部查询继续处理, 不应仅因 Worker 退出就重新创建外部请求.

理由: Human Approval 等长等待不应依赖 Worker 持续存活, 统一领域语义不要求所有 Handler 使用同一执行协议.

未采用的替代方案: 长等待必须由常驻 Worker 保持, 或重启后一律重新发起操作. 仅明确支持相应能力的 Handler 使用此协议.
外部请求已创建而等待事实未提交的窗口仍可能 Unknown; 回调登记、认证和去重待定.

### Q15: 持久状态支持恢复, 通知用于降低延迟

待处理操作必须能从持久状态重新发现, 已提交 Outcome 必须能查询. 调度唤醒与 Outcome 到达通知不作为唯一恢复依据;
通知丢失不应使已提交操作永久不可发现.

理由: 覆盖提交后、通知发送前崩溃的窗口, 避免调用进程或一次消息送达成为恢复前提.

未采用的替代方案: 仅依赖内存队列或一次消息派发/完成通知. 本决策不允许随意丢弃 Worker 结果报告;
报告持久化与确认协议需要另行定义. 状态扫描、Transactional Outbox 或组合方案尚未选择, liveness 假设待定.

### Q16: Outcome 分类为 Succeeded / Failed / Cancelled

Succeeded 表示接受了操作契约定义的正常完成结果, 不要求业务结果正面; Failed 表示接受明确操作错误,
或根据已知事实与策略决定无法正常完成; Cancelled 表示接受停止继续处理的决定, 不证明外部停止.

理由: 核心完成方式与业务含义不同, 例如审批拒绝可以是正常完成的结果. 具体原因属于结果或错误数据, 不新增 Timeout / Unknown
/ Rejected 等核心终态.

未采用的替代方案: 将业务拒绝一律映射为 Runtime 失败, 或用超时、重试预算耗尽将未知执行伪装为失败. 已接受 Unknown
不产生终态的原则不变; 最终失败的一般守卫见 Q24, Handler 错误契约待定.

### Q17: Outcome 属于 Intent, 来源不必是单个 Execution

普通 Handler 完成应保留 Execution 关联; 未创建 Execution 就取消等控制面终结无需伪造尝试. Authority 策略终结与
reconciliation 应记录明确来源、理由及证据关联, 不强制所有 Outcome 均引用单个 Execution.

理由: 权威结果属于逻辑操作, 其合法来源还包括控制面决策. 来源建模应表达真实因果关系.

未采用的替代方案: 为非执行终结创建虚构 Execution, 或允许无证据成功. 具体来源类型、证据关系和成功守卫仍待定义.

### Q18: 合格终结候选按原子提交裁决

取消与合格完成竞争时, 第一个通过全部验证并完成权威事务提交的终结决定获胜. 不按 Worker 墙上时钟或请求发送时间追溯改写.
Outcome、Intent 终态与对应历史必须一次原子提交.

理由: 已提交 Outcome 不可变, 外部实际完成与权威接受是不同事实. 任何候选仍须通过身份、资格与当前状态检查;
此规则不允许任意先到报告获胜.

未采用的替代方案: 取消天然优先, 或根据迟到时间戳改写终态. 竞争失败方的报告与决策事实可以保存, 但不能生成第二个 Outcome.

### Q19: Worker lease 与 Execution 结果资格分离

Worker lease 管理短期领取、启动授权、续租和协调权限. lease 到期不自动撤销 Execution 的结果接受资格; Authority
可以验证并接受未撤权尝试的迟到结果. 授权替代尝试前应明确处理旧尝试资格, 并符合 Q3.

理由: 临时 Worker 权限不等于外部操作寿命或结果有效期限, 长等待也不应依赖数周 Worker lease.

未采用的替代方案: lease 到期即外部停止或结果永远无效. 报告由 Authority 验证与提交, Worker 不得绕过资格检查写 Outcome;
Runtime 权限并不自动成为外部服务的 fencing 保证. 具体时间依据、token 与启动守卫尚未确定.

### Q20: 持久化报告确认不同于 Outcome 接受

报告协议区分已持久化、Outcome 已接受以及未采用/待协调. 发送方可以按协议在报告已持久化后停止重投该报告, 不要求其必须赢得
Outcome. Durable 模式下不得在证据落盘前确认已持久化.

理由: 撤权尝试的结果仍可成为证据; 通信重投不应演变为重复外部执行, 也不应仅因未被采用就无限重发.

未采用的替代方案: 含糊的单一 OK 或持久化前确认. Worker 未获确认前崩溃且未保存自身报告仍可能 Unknown;
本决策不承诺消除所有结果丢失窗口. 报告身份、冲突去重与证据存储尚未确定.

### Q21: Intent 生命周期为 Open / Closed

Open 表示没有 Outcome; Closed 表示已有不可变 Outcome, 不再授权新的 Execution. Succeeded / Failed / Cancelled 由 Outcome
表达, 不在 Intent 重复保存结果分类. 不变量: Intent 为 Closed 当且仅当存在 Outcome.

理由: 逻辑终结与尝试进展分离, 避免将运行、等待和恢复诊断都提升为 Intent 权威生命周期状态.

未采用的替代方案: Intent 同时保存多套终态分类, 或把所有操作视图压成互斥状态. Open 本身不足以指导调度;
重试时间、等待关联与安全阻塞依据仍需持久化或可从持久事实推导.

### Q22: 外部执行前必须持久化启动授权

Worker 调用可能产生副作用的 Handler 前, 必须取得 Authority 已持久化的启动授权. 授权前合规 Worker 不得执行;
授权后缺少开始或完成报告, 仍应考虑外部操作可能已发生.

理由: 避免外部执行先于授权事实落盘的窗口, 并防止依据没有 Running 报告推断未执行.

未采用的替代方案: 先执行再上报开始, 或将授权等同真实外部开始. 授权后、调用前崩溃可能造成保守 Unknown;
启动授权不跨数据库与外部系统原子化, 也不保证外部执行恰好一次. 授权身份与重复响应语义待定.

### Q23: 传输重投不创建新 Execution

同一次派发重复投递保留同一个 Execution 身份. 新 Execution 表示 Authority 明确授权的执行重试, 必须遵守安全条件;
不因发送超时或确认丢失自动建立新尝试.

理由: 传输重投、报告重投和外部重新执行是不同协议动作, 不应共享一个含糊的 retry.

未采用的替代方案: 每次重发消息都建立新 Execution 或直接重新调用 Handler. 接收方仍须验证领取与启动资格; 同一 Execution ID
本身不是外部幂等保证.

### Q24: 最终失败需要明确守卫

Failed Outcome 至少需要明确错误或终结依据、策略决定不再尝试, 且不存在未解决并仍可能改变逻辑操作结果的不确定性.
预算耗尽本身不能将 Unknown 转成 Failed; 允许继续协调或显式取消.

理由: 策略不再重试不等于已知操作失败. 已知契约错误可以合法失败, 即使产生过部分副作用; Failed 不证明外部什么都没发生.

未采用的替代方案: 超时或重试预算耗尽自动产生失败终态. 具体错误证据和契约守卫由 Handler 与 Runtime 共同定义,
不要求证明外部世界不存在任何副作用.

### Q25: Execution 生命周期与结果资格正交

尝试进展与是否有资格直接成为 Outcome 候选是两个领域维度. 明确撤权不作为 Execution 生命周期终态, 不阻止后续保存真实结果;
等待中的尝试可以仍有资格, 已报告成功的尝试也可以已被撤权.

理由: 资格变化不等于外部尝试结束, 不能用一个互斥状态丢失进展或权限信息.

未采用的替代方案: Revoked 成为不再接收事实的 Execution 终态. 领域维度分离不要求重复存储字段; 当前尝试指针、generation
与具体约束待选择.

### Q26: Execution 使用五种协议状态

采用 Prepared / StartAuthorized / Waiting / Unknown / Resolved. 状态表达 Runtime 掌握的协议事实, 不是直接观察外部世界.
Dispatched 属于审计事实, Succeeded / Failed 属于尝试结果数据; Worker lease 到期本身不使已登记的 Waiting 变成 Unknown.

理由: 区分启动许可前后、可恢复等待、不确定性和已接受的确定结果, 同时避免状态名暗示真实外部执行保证.

未采用的替代方案: 将 Dispatched / Running 当作安全事实, 或将 Unknown/Revoked 当作不可再接受证据的终态. Resolved
不代表证据绝无争议, 具体冲突投影规则待定. 当前状态与主路径见核心状态机 SPEC 草案.

### Q27: 矛盾报告保留证据并协调

重复报告可去重, 内容矛盾的报告不可覆盖, 不按最后写入或时间戳选择结果. 尚无 Outcome 时, 已知冲突阻止未经协调的自动终结;
已有 Outcome 时不改写它, 但保留冲突供调查.

理由: 报告是证据, 不是可以最后写入覆盖的权威事实; 已知矛盾需要可信来源与协调依据.

未采用的替代方案: 最后一次报告获胜, 或已有 Outcome 后丢弃冲突. 协议不能预知未来报告, 不承诺阻止未来才暴露的矛盾;
报告身份和冲突处置细节待定.

### Q28: 启动许可绑定 Worker incarnation

启动许可绑定某次 Worker 存活实例, 使用可序列化 incarnation 身份而非 PID. Worker 重启产生新 incarnation,
不直接复用旧许可调用 Handler; 派发或许可响应重投不表示再执行一次.

理由: 避免把旧启动许可当作重启后的重复调用授权. 已授予许可的恢复应走协调或符合 Q3 的新尝试流程.

未采用的替代方案: 同设备新进程自动继承旧启动许可并重新调用. 此机制不阻止旧实例在不配合 fencing 的外部系统上迟到执行;
权限验证、许可请求去重与恢复细节待定.

### Q29: 普通合格完成尽量一次事务终结

默认在同一本地事务保存普通合格完成报告、更新 Execution、插入 Outcome、关闭 Intent 并记录历史.
已撤权、矛盾或待查询报告可以仅保存证据, 返回未采用/待协调.

理由: 减少正常路径中间状态, 同时允许不合格证据独立持久化. 一次提交可以同时确认报告已持久化与 Outcome 已接受;
两种确认含义不强制两次事务.

未采用的替代方案: 强制所有正常完成先持久化报告再异步终结, 或为了合并路径拒绝保存迟到证据. 具体 Storage 接口、锁或 CAS
机制尚未选择.

### Q30: 首选五个明确的逻辑存储实体

采用 intents / executions / outcomes / reports / history 作为关系存储首选方案. reports 保存
Pending、完成、查询及协调产生的不可覆盖证据; history 保存状态转换、资格变化、决定与冲突的审计事实. 审计可引用报告,
不必重复复制全部结果内容.

理由: Execution 的多个报告可以迟到、冲突或暂不成为 Outcome, 不能用一个可覆盖 result 字段承载. 证据说明收到什么,
历史说明为何如何处理, Outcome 说明最终接受什么.

未采用的替代方案: 为坚持四表而把所有报告嵌入 Execution 集合字段, 或混入只为状态转换设计的历史结构;
两张通用状态机表也不作为首选. Report 不是新的核心状态机, IEO 主干不变. 物理字段、证据保留与查询索引尚未确定.

### Q31: 纯领域决策与原子持久化分离

领域快照与命令产生拒绝理由或待提交的状态变化和事实. 决策不直接访问数据库、网络或时钟,
时间、权限、策略与证据作为显式输入. Coordinator / Storage 在原子边界内加载必要状态并执行、提交,
防止并发状态变化使决定失效.

理由: 相同输入可得到可重复的决策, 规则可独立测试和映射到 Quint; SQLite 与 PostgreSQL 的并发机制不进入领域规则. Storage
Interface 围绕完整原子领域操作, 不是暴露 CRUD 让调用方拼装一致性.

未采用的替代方案: Handler 直接访问 Ecto Repo, 每个调用方自行维护事务和状态约束, 或建立通用状态机框架.
纯函数本身不能解决竞态或自动证明实现正确; 完整事务 Interface 与冲突重判规则待定.

### Q32: Durable 一致性不依赖单个 Coordinator 进程

可以使用 OTP / GenServer 组织工作, 但 Durable 后端必须通过实际事务与并发约束独立保障不变量. 多个 Coordinator
同时处理同一 Intent 时仍不得产生重复 Outcome 或不一致组合状态. 不同 Intent 不要求全局串行.

理由: 防止把正常部署的单进程假设误当成故障恢复与多实例正确性保证.

未采用的替代方案: 只靠单个 GenServer 持有写入资格. 具体唯一约束、锁或条件更新由 SQL 后端实现,
不要求所有后端使用相同机制.

### Q34: 第一阶段默认持久状态扫描, 不强制 Outbox

默认通过数据库中的待处理状态与必要调度数据重新发现工作, 配合可丢失的唤醒通知. 扫描覆盖派发与其他必要恢复工作;
派发重投仍保留 Execution 身份并验证启动资格.

理由: 当前目标是恢复仍需处理的工作, 不是向外部消费者可靠发布每一个中间历史事件.
减少第一阶段独立队列与消息发布状态的维护成本.

未采用的替代方案: 把 Transactional Outbox 设为核心必需设施. 若以后需要逐事件可靠发布可增加 Outbox;
其事务原子入队不保证消息不重复或外部执行恰好一次. 扫描索引、频率、认领和公平性尚未确定.

### Q35: 第一阶段排除独立 Memory/ETS Storage

Q33 的中立意见经本决策明确: 第一阶段只正式支持 SQLite 与 PostgreSQL 两类 Ecto 持久化后端, 不提供独立 Memory/ETS Storage.
纯领域测试使用普通数据快照; 存储一致性与故障测试使用真实 SQL 后端. ETS 若未来用于缓存, 不承担权威存储职责.

理由: 当前没有明确需求值得增加第三种 Adapter 的原子性、并发读取、owner 生命周期与 conformance 验证成本. 可替换的 Storage
Interface 已由两类 SQL 后端形成真实需求, 不需要额外 Memory 后端来证明抽象.

未采用的替代方案: 为测试方便先实现 Memory/ETS Adapter, 或为了统一接口弱化 SQL 原子保证. SQLite 临时数据库可用于集成测试;
PostgreSQL 必须有自己的并发验证. 具体后端发布顺序、数据库配置与版本尚未确定.

### Q36: 契约版本编入 Operation Identity

使用 llm.generate.v1 等稳定 Operation Identity 表达输入、结果及操作语义契约. 保持契约的修复可继续使用同一 Identity;
不兼容变化使用新 Identity. 旧 Intent 必须由兼容 Handler 解释, 不自动套用新版本.

理由: 用单一明确身份约束最重要的解释兼容性, 不将代码发布版本当作契约版本.

未采用的替代方案: 第一阶段建立通用 Schema Registry, 以 Schema Hash 替代版本, 或自动将旧 Intent 指向最新 Handler.
数据库与 Runtime 协议迁移仍需独立设计.

### Q37: 受限纯数据契约先于 codec

持久输入、结果、策略和等待数据采用运行时无关的受限结构化值域, 基础值域接近 JSON. 不持久化 PID / Reference / Function /
Port 等运行时对象. 数字范围以及大整数、字节、时间和产物引用的表示需明确约定.

理由: 可编码不等于可恢复解释. 先确定合法值与解释语义, 再验证 SQL 和网络 codec 的 round-trip.

未采用的替代方案: 任意 Erlang term 原样持久化, 仅靠 binary_to_term safe 作为 schema 或资源安全保证, 或认为所有合法 JSON
都满足所有后端限制. 本决策不强制所有存储与网络采用 JSON, ETF 可否作为受限值的 codec 待定.

### Q38: Report 使用稳定身份

Report 在约定作用域内有发送方提供的稳定身份, 重投保持身份和内容. 同身份同内容按重复接收处理;
同身份不同内容作为冲突另存证据且不覆盖; 不同身份同内容可以是独立证据, 不自动合并.

理由: 传输重投与重复观察不是同一概念, 内容 hash 不能单独定义报告身份.

未采用的替代方案: 仅用内容 hash 去重所有报告, 或在重投时生成新报告身份. hash 可以辅助一致性检查;
作用域、内容等价和冲突证据存储待定.

### Q39: Handler 能力显式声明且带条件

Pending、查询、尽力取消/确认停止、幂等与安全重复等能力必须显式声明, 未声明按不支持处理.
幂等需有适用范围、有效期与其他条件, 不能仅靠静态 supports_idempotency 布尔值授权重试.

理由: 能力名称不等于所有情况下都成立的保证, 查询也不总能证明未执行. 策略必须根据具体条件判断重试与协调权限.

未采用的替代方案: 所有 Handler 默认支持查询、取消或幂等, 或将声明当成证明. 外部协议与测试仍是必要依据;
能力的持久快照与具体契约字段待定.

### Q40: 外部回调由专用 Adapter 验证转换

Handler 或回调 Adapter 验证第三方来源、解析业务内容后形成 Report. 核心统一验证 Intent / Execution 关联、报告身份、资格与
Operation 契约, 不直接将未经验证的回调正文作为 Outcome.

理由: 第三方签名和消息格式属于外部协议, 权威接受属于领域规则; 可恢复关联不能只存在于进程邮箱或内存映射.

未采用的替代方案: 核心理解每个平台的专有 HTTP 回调, 或合法回调必须依赖原 Worker lease 存活. 不默认所有平台支持回调,
关联建立时机与乱序处理待定.

### Q41: 不可变提交定义与当前控制数据分离

Intent 保留不可变提交定义: Operation Identity、输入、必要硬执行约束和初始策略快照.
当前预算、节奏等控制/调度数据另行维护, 通过明确受控命令调整并记录历史, 不通过相同 key 重提交隐式覆盖.
调整不能偷偷改变输入、目标或放宽副作用安全条件.

理由: 恢复时仍能解释原始请求, 同时允许操作在相同逻辑身份下被受控管理. Submission Key 比较原始定义,
不比较尝试次数和当前调度状态.

未采用的替代方案: 每次重试修改原始请求, 或把当前控制状态纳入重复提交相等性. 具体可调整字段、权限、revision
与冲突处理待定.

### Q42: Submission Key 为持久 namespace + key

在同一个权威数据集合内, 调用方显式提供 namespace + key 来重新定位 Intent. 不以 Worker、进程或设备身份作为作用域; Agent
重启及计划迁移保持该身份. 同作用域相同 key 不对应两个不同 Intent; 无 key 的提交仍建立新操作.

理由: 输入相同不代表操作相同, 但提交确认丢失和上层恢复需要找到原逻辑请求. namespace 不提供认证或权限证明.

未采用的替代方案: 进程级作用域、默认全局 key 注册中心或输入 hash 去重. 上层需要保存/重建稳定身份, Runtime
不推断业务等价; 权威数据集合路由与身份保留周期待定.

### Q43: 启动时记录 Handler 与相关能力条件

启动授权时记录实际 Handler 标识及影响恢复、安全重试的能力条件快照. 后续不能只看当前部署的能力声明;
需知道原外部协议、作用域及当前条件是否仍成立.

理由: Handler 升级不能抹去原尝试的解释依据. 快照是历史依据, 不是永远有效的保证.

未采用的替代方案: 恢复时只使用最新声明, 或要求永久保留原代码进程/二进制. 兼容实现可以查询或处理回调,
但不可无声改变已采用的协议; 快照字段与兼容验证待定.

### Q44: 幂等上下文属于 Intent

可靠外部幂等可用时, Runtime 提供随 Intent 保存的稳定幂等上下文, 不同 Execution 复用并在迁移中保留. Handler
按外部协议映射键与作用域, 多步骤可按契约派生稳定子键.

理由: 每次重试生成新外部键会被目标服务视为新操作. 逻辑操作去重与尝试身份不应混同.

未采用的替代方案: 使用 Execution 或 Worker incarnation 生成每次变化的外部键, 或假定一个键自动覆盖全部子步骤. 它不同于
Submission Key, 也不使不支持幂等的服务获得保证.

### Q45: 回调关联先于外部操作, 处理乱序

回调型 Handler 最迟在启动授权提交时建立持久完成关联, 不等 Pending 返回才登记. 验证后完成可以先于 Pending 被处理; 迟到
Pending 不将已解决尝试退回 Waiting.

理由: 快速完成与消息乱序可能使外部回调先于 Worker 报告, 不能让回调只因登记顺序丢失归属.

未采用的替代方案: 只在 Pending 后创建关联, 或把 Worker 启动许可直接用作第三方回调凭证. 关联身份不等于认证凭证,
也不意味着仍有 Outcome 资格; 已撤权或关闭时仍可保存合法证据.

### Q46: 同一 Intent 的决定共用原子并发边界

影响执行资格、结果判断或终结的命令按同一 Intent 协调: 建立/替代尝试、启动授权、接受
Pending/完成/冲突证据、撤权、终结及相关控制变更. 保存影响判断的报告不能绕过协调, 让并发命令继续基于过期证据自动终结.

理由: 同一 Intent 的决定需要一致的提交顺序, 不同 Intent 不需要全局串行.

未采用的替代方案: 各实体分别保存而只在插入 Outcome 时处理竞争. 使用锁或版本条件由后端实现; 不建立全局锁或全局
Coordinator.

### Q47: 当前 Execution 关联表达正常候选资格

Intent 保存可为空的 current_execution_id. 正常完成须属于当前尝试、Intent Open, 且满足来源、证据和其他守卫.
替代尝试时原子建立新 Execution 并切换关联, 旧生命周期不被伪造结束, 报告仍可保存; reconciliation 可以明确验证使用旧证据.

理由: 第一阶段无主动 hedging, 一个当前关联比多个独立 eligible 布尔值更易维持单一资格. 当前关联是资格的一部分,
不是完整提交许可.

未采用的替代方案: 每个尝试独立维护可能同时为真的正常资格标记. hedging 是为同一 Intent 同时授权多个尝试竞速, 不同 Intent
的并发不属于 hedging.

### Q48: 无启动授权时可换 Worker, 授权后不无条件接续

Prepared 且权威记录确认从未授予启动许可时, 旧领取资格失效后可以让新 Worker 领取同一 Execution. 已授予许可则新
incarnation 不继承旧许可重新调用; 再次执行必须是符合安全条件的新尝试.

理由: 启动前可以安全重新分配传输和领取, 启动后必须保守对待可能已发生的外部操作.

未采用的替代方案: 依赖 Worker 声称没收到许可/没执行, 或每次派发确认丢失都建立新尝试. 分界以 Authority 原子检查为准.

### Q49: lease 到期不立即替换尝试

Authority 判定到期后旧 lease 不再提供相应临时控制权. 有效 Pending 继续等待; 已授权且无可靠结果/等待登记时可标 Unknown,
保留当前尝试结果资格. 先等待迟到结果或协调, 满足安全条件后才原子切换新尝试.

理由: 自动故障怀疑与自动重试不同, 既不能浪费合法迟到结果, 也不能以到期证明旧操作停止.

未采用的替代方案: lease 到期立即接管并重新调用 Handler. 时间依据、续租和重启规则仍待确定.

### Q51: 上层维护业务集合, Runtime 提供基本恢复

收窄并解决 Q50 的责任归属: 上层自行持久化业务恢复集合与等待关系, Runtime 默认承担已接受 Intent 的最小派发、lease
检查及必要执行恢复. 暂不要求统一 next-action 投影, 不建立通用 Job 模型.

理由: 上层解决恢复哪些计算和如何继续决策, Runtime 解决已接受操作如何可靠继续处理,
避免每个调用方重复实现失联检测与执行资格规则.

未采用的替代方案: 默认让每个上层负责全部执行恢复, 或把 Runtime 恢复直接实现为必须全表遍历. 可用持久事实和索引发现候选,
必要时再补调度字段. 调度策略与工作发现实现可替换, 但处理通过原子领域命令, 不让上层绕过规则直接改表.
未批准统一投影的字段形态.

### Q52: lease 使用 Authority 时间依据

持久 lease 到期判断使用 Authority 侧时间, 不以 Worker 时间戳裁决. PostgreSQL 在原子命令路径取得当前数据库时间,
不将长事务起点 now 当作验证当刻; SQLite 使用权威操作路径中的当前 VFS 时间. 领域纯函数接收显式时间输入,
权限检查在原子边界内执行.

理由: 避免跨 Worker 本地时钟互比, 明确验证采样点. 数据库墙钟仍可能跳变, TTL 不保证实际经过时间的精确上界.

未采用的替代方案: 持久化裸 Worker monotonic expiry, 或将所有数据库当前时间函数视为等价. 具体精度与实现需按部署验证,
保持事务短小且不执行外部操作.

### Q53: 重新领取分配新 generation

每个 Execution 的临时领取权限使用 Authority 分配的持久 generation 并绑定 Worker incarnation. 重新领取增加 generation,
普通续租不更换它; 旧代不能续租、申请启动或执行旧 lease 保护的控制动作. generation 不重置复用.

理由: 同设备或同 Worker 名称不足以区分旧请求, 当前代与 incarnation 必须共同验证.

未采用的替代方案: 仅验证 Worker 名称, 或把旧代报告一律丢弃. 报告与 Outcome 资格独立; generation 只在相应权威历史内有效,
不独自阻止旧数据库副本写入.

### Q54: 确认失效后不因时钟回拨复活

验证 now < expires_at 才未到期, 相等算到期. 续租要求当前 incarnation、generation 且尚未失效. Authority
事务确认到期/撤销后持久化失效事实, 墙钟后跳不能让该代再次有效. 新领取需要新 generation, 不代表第二次启动授权.

理由: 系统墙钟被调回更早时刻时, 不能仅凭过期时间再次落在未来就恢复旧权限.

未采用的替代方案: 每次只比较墙钟而无持久失效依据. 若后跳发生在确认之前, 仍可能延迟检测; 不承诺消除所有时间跳变影响.

### Q55: History 不逐条记录普通心跳/续租

强制记录领取与 Worker/generation 变化、权威到期/撤销、启动授权、失联 Unknown、替代尝试及安全依据.
普通心跳/续租默认不逐条进入领域 History, 但当前 lease 更新仍原子验证, 不绕过并发边界.

理由: 保留解释资格变化的必要事实, 避免长时间操作产生低价值历史. 普通诊断日志与指标可另行保留.

未采用的替代方案: 将每个心跳写入领域审计, 或省略历史同时省略一致性检查. History 不承担重放所有心跳的职责.

### Q56: 普通 Coordinator 重启与 Authority 迁移分开

权威数据库未迁移的普通 Coordinator 重启重新验证持久状态, 不默认让所有远程 lease 失效. 正式 Authority 迁移在新 Authority
激活前使旧临时 Worker lease 失效, 保留 Execution、启动证据、当前结果资格及 Pending 完成关联.

理由: 普通重启不无端打断远程工作, 跨 Authority 迁移不沿用不同时间环境下的临时权限.

未采用的替代方案: 一切重启都重执行, 或迁移后沿用旧控制权限. 已授权尝试不得重置 Prepared; 合法迟到报告仍可验证.
本决策不替代一致切点与旧 Authority 撤权协议.

### Q57: 负面查询不单独授权危险重试

not_found、尚未开始或暂无结果默认仅为协调证据, 不单独证明可安全重试. 不可重复操作还须排除旧尝试/在途请求以后执行,
或由可靠外部幂等/fencing 覆盖重复窗口, 或由调用方明确接受重复风险.

理由: 已获启动许可的旧 Worker 可能暂停在发送请求前, 外部查询此刻未发现操作仍不能排除它后来执行.

未采用的替代方案: 支持查询就等于查询不到即可重试, 或用普通负面查询自动把尝试标为确定结束.
可信的未执行证据必须有协议依据, 不能仅验证响应内容.

### Q58: 首个 Quint 模型限定核心 Safety

已批准建立单 Authority、一个 Intent、两个 Worker、最多两个 Execution 的小型模型.
聚焦当前尝试、generation/incarnation、启动、迟到结果、取消竞态和时钟跳变. 数据库提交抽象为原子动作, 不模拟 SQL、完整
Agent、Authority Transfer、版本迁移或大型数据.

理由: 优先得到可执行、可定位反例的核心规格, 不一次建模所有架构层. 运行 typecheck/test/run 场景与抽样模拟,
明确不声称穷尽证明或 Ecto 实现正确.

模型应包含故障场景、可达性见证及故意错误规则的反例检查, 不用没有进展的模型获得虚假信心.
状态组织和系统假设需在写逻辑前确认, 工具链已有 Quint 0.32.0; 实际后端可执行性需运行核验.

### Q59: 首个模型的状态分组与 plain Quint

已确认五组独立状态: Authority 的持久账本与在线状态、Worker
的存活/incarnation/已收许可/调用状态、无序消息集合、真实外部调用与资源事实、可前后跳变的 Authority 整数时钟.
外部事实不能自动成为 Runtime 知识; 收到并验证报告后才更新证据与结果.

使用 plain Quint, 不引入 Choreo. 此模型以单个原子 Authority 为中心, 两个 Worker 的协议范围有限;
手写消息集合更便于直接审查许可与提交窗口. 将来扩大多节点协议时重新评估框架, 不据此推导所有分布式模型都不用 Choreo.

独立记录终结提交、首次结果及启动/替代决定的见证, 避免单个 Outcome 字段使唯一性成为类型上的同义反复.
这些辅助见证不等于已经批准的物理存储字段.

### Q60: 首个模型的故障与持久化假设

Worker 可崩溃丢失易失状态, 以新 incarnation 重启; 消息可延迟、乱序、重复与丢失. Worker 遵守启动协议, 不模拟 Byzantine
伪造. Coordinator 可停止与恢复, 已提交权威事务不回滚. 获授权旧 Worker 不因 lease 到期自动停止.

不假定最终投递、人工最终响应或调度公平性, 不作 Liveness 保证. 数据库原子性与已提交持久性是模型前提, 不是
SQLite/PostgreSQL 任意配置的实证结论.

首个可执行规格、场景及故意错误规则见 [核心模型](../quint/README.md). 运行结果仅针对指定边界和抽样路径;
模型中的收窄选择与未覆盖协议在该文档单独列出, 不自动成为新产品要求.

### Q61: 冲突独立于 Execution 生命周期

收到矛盾报告时保留全部证据, 独立持久化未协调冲突. 报告冲突本身不让生命周期按最后一份报告来回切换;
保留最近一次有依据的生命周期投影. 例如 Resolved 后发现矛盾仍保留 Resolved, 同时标明其结果存在未协调争议.

未协调冲突阻止自动结果采用. 解除阻塞需要明确 reconciliation, 不能覆盖原始报告或只凭新报告把冲突标志清除. 已有 Outcome
仍不可改写; 显式 Cancelled 按已确认规则处理.

理由: 执行进展、结果资格和证据争议是不同维度. 不增加混合这些含义的 Conflicted 生命周期状态. 本决策不冻结 lease
到期等独立合法转换, 也不批准具体冲突字段或协调命令.

### Q62: 旧成功证据未协调时阻止普通 Failed

旧尝试已失去直接结果资格, 但收到的成功证据仍可能改变 Intent 的逻辑结论. 当前尝试已知失败时, 不得忽略旧成功而普通提交
Failed; 必须先 reconciliation, 按 Operation 契约明确采用或排除这份证据.

旧成功不直接抢占 Outcome, 失去资格也不等于证据失去意义. 原始报告保留, 已知事实不能仅因 current 切换而消失. 显式
Cancelled 仍可按既定规则终结, 不把争议伪装成确定失败.

理由: “所有尝试都有已知结果”不充分证明整个 Intent 可以 Failed. 资格与证据意义分开. 证据未明确处置时保守阻止普通 Failed,
不伪造已协调状态. 协调提交原则与触发范围已在 Q63/Q64 确认; 具体权限、依据表示、命令身份的表示与物理存储仍待设计.

### Q63: 协调提交明确可审计的证据处置决定

协调通过显式原子领域命令提交, 引用具体报告、Operation 契约依据、理由及处理主体,
明确采用的结果与排除的证据对本次判断的影响. 原始报告保留, 不用一个永久的“已协调”标志代表全部证据已经处理.

Authority 在同一 Intent 原子边界重新验证当前证据与资格, 保存 History, 再解除对应阻塞或提交 Outcome.
新增证据仍需重新判断; 不把旧处置自动扩展到未审查报告. 命令身份原则见 Q66;
具体身份表示、处置范围表示和并发验证方式尚待设计.

理由: “完成协调”必须可解释处理了什么和为什么, 不能成为绕过普通终结守卫的通用后门. 本决策不增加通用 Workflow
或要求新的独立逻辑表.

### Q64: 契约规则自动协调与人工显式协调并存

第一阶段允许明确登记、条件可验证的 Operation 规则自动协调, 也允许获授权主体提交人工显式决定.
没有适用规则或证据不足时保持待协调, 不默认用启发式选择报告.

自动与人工决定都满足证据、资格、原子提交和审计规则. 人工入口不提供任意覆盖 Outcome 的能力;
自动规则声明本身也不等于条件已经成立. 规则身份、版本、授权方式和外部条件核验契约尚待具体定义.

理由: 能按协议确定的处理可自动推进, 不确定判断保留明确责任与依据, 无需通用协调 Workflow.

### Q65: 过期人工决定拒绝, 自动规则重新求值

人工审查后, 提交前影响判断的证据或资格发生变化时, Authority 拒绝过期决定并返回当前判断上下文, 要求重新审查.
不在提交时悄悄改变人工批准的含义. 普通心跳等不影响判断的变化不应使决定过期.

已登记自动规则可以针对新上下文重新求值, 但必须形成新的可审计决定, 而不是把旧处置扩展到新证据.
具体判断作用域、版本表示和返回结构仍待设计.

理由: 人工批准与实际生效的决定须一致; 自动化也须解释其审查的证据与依据.

### Q66: 协调命令具有 Intent 范围内的稳定身份

协调命令使用 Intent 范围内稳定的命令 ID. 同一 ID、相同命令内容的重投返回原处理结果, 不再次执行决定或追加同一决定的
History. 同一 ID 携带不同内容则拒绝, 不覆盖原命令或决定. 命令身份与 Submission Key、Report ID 分开.

重投不使原决定适用于后来出现的新证据, 也不重新提交或改写 Outcome.
对已提交命令的重投识别应先于新的证据快照和终态资格判定; 权限与返回内容的访问控制另行验证. 同一 ID
下的内容相等是领域内容相等, 不据此批准某种字节编码.

理由: 响应丢失后调用方需要知道原提交是否成功, 不能将当前不可执行误报为原提交失败.
领域拒绝的身份固定与权限变化后的结果读取已由 Q67/Q68 确认; 记录保留原则见 Q69; 具体归档/清理与鉴权协议仍待设计.

### Q67: 明确领域拒绝也固定命令身份与原处理结果

请求经过权限与格式校验进入领域处理后, 过期审查、当前不可采用等明确领域拒绝也持久固定命令 ID、请求内容和当时结果. 同 ID
同内容重投返回原拒绝; 同 ID 不同内容拒绝. 重新审查或要求重新判断时使用新 ID, 不在旧身份下重新求值.

通信失败或未提交的数据库异常可重投原请求. 身份/权限/格式校验失败不据此占用领域命令身份. 拒绝提交须保留审计,
不制造协调决定或 Outcome.

理由: 同一请求的结果必须稳定, 避免重投将原先被拒绝的请求后来执行. 返回原拒绝中的上下文属于原处理时刻, 不是当前 Intent
快照.

### Q68: 提交权限与原结果读取权限分开验证

新决定要求当前提交权限; 读取已处理命令的原结果要求当前读取权限. 已失去提交权限但仍有读取权限时, 可确认原成功或拒绝结果,
不重新执行决定.

失去读取权限后拒绝返回结果内容, 但保留原命令记录与身份. 权限变化不能把原命令重新解释为未处理请求.
实际身份绑定、授权策略及权限变化的原子校验协议仍待设计.

理由: 操作权限与查看历史结果的权限用途不同, 而权限撤销不应破坏命令去重与持久事实.

### Q69: 命令身份与原结果随 Intent 保留

第一阶段在 Intent 仍被保留时, 持续保留已处理命令的身份、内容相等性所需信息和原处理结果, 不默认通过 TTL 清除. Intent
Closed 也继续保留.

后续归档或清理须有明确协议, 保证旧 ID 不会重新可执行, 并说明原结果是否仍可查询. 本决议不批准删除
Intent、重用已删除身份或具体清理机制.

理由: 任意延迟的重投仍须识别原处理结果; 清除去重数据不能使原命令成为新请求.

### Q70: 判断版本检测审查过期

Intent 维护单调递增的判断版本, 协调命令携带审查时的版本. Authority 在 Intent 原子边界比较版本, 再核验证据、Operation
契约与当前权限. 版本相同不代表决定本身合格.

影响判断的新证据、当前尝试或结果资格变化, 以及影响后续判断的协调处置等持久变化使版本递增.
普通心跳、命令重投和纯拒绝审计不递增. 具体报告引用继续保留以解释决定; 外部条件仍须在提交时核验.

理由: 检测读取材料与提交决定之间的相关变化, 避免提交时静默改变人工决定. 本决议选择版本校验机制, 不批准通用状态
revision、代码版本或以时间戳代替判断版本; 具体字段、变化清单及 SQL 校验仍待细化.

### Q71: 协调决定覆盖完整相关冲突

协调矛盾报告时, 决定须覆盖本次判断相关的全部冲突报告, 说明采用或排除各项证据的 Operation 契约依据,
不能只选择有利证据而隐式解除其他冲突.

Authority 在同一 Intent 原子提交中保存明确处置、解除对应阻塞, 并在终结条件满足时提交成功或失败 Outcome. 原始 Report
和冲突历史继续保留; 新证据需要重新判断, 不能沿用旧处置自动解除其阻塞.

理由: “冲突已解决”须可审查, 能解释具体处理了哪些矛盾. 具体相关性范围、证据处置表示与各 Operation 的核验规则仍待细化;
本决议不赋予任意改写已有 Outcome 的能力.

### Q72: 全部排除后仍保持结果未知

允许按 Operation 契约逐项记录对全部相关矛盾报告的排除, 完成这组冲突的审查处置, 同时保持结果未知、Intent Open.
原报告、冲突历史、命令及处置审计保留.

该处置不生成成功或失败 Outcome, 不把没有可采信证据解释为未执行, 也不自动授权重试. 后续继续收集证据,
或按已有独立安全条件决定下一步. 新证据仍须重新判断.

理由: 可以明确知道现有报告都不能用于本次判断, 而仍不知道外部操作的实际结果. 排除依据须经过 Authority 校验,
不是任意丢弃不利证据.

### Q73: 显式取代先前证据处置

新决定改变先前证据处置时, 须明确引用被取代的旧处置及对应范围. Authority 在同一 Intent
原子边界重验审查版本、具体引用、证据、Operation 契约和权限, 保存新决定与取代关系、审计并更新当前适用关系.
只取代明确范围, 不靠“最后写入获胜”隐式覆盖其他处置.

旧决定、原始报告、历史冲突及各命令的原处理结果继续保留. 原命令重投不因其决定后来被取代而重执行或返回新结果.
新证据仍须重新判断, 已有 Outcome 不可修改.

理由: 同一报告可能先排除后采用, 也可能由采用转为排除. 审计应解释当前判断源自哪项决定、取代了什么及为何成立.
具体决定身份、关系字段、表示和 SQL 实现尚待设计.

### Q74: 自动决定绑定规则语义版本

每项自动协调决定明确引用规则身份及语义版本. Authority 在提交时核验该确切版本仍被登记且适用条件满足,
同时重验证据、Operation 契约、审查版本和当前权限. 不默认为规则的最新版本, 不把旧请求静默迁移到新版本.

历史决定按当时规则版本解释, 原命令重投返回原处理结果, 不按新版本重新求值. 自动重新求值产生新决定时,
明确使用所选规则版本、当前审查上下文与新的命令身份. 规则语义版本与 Handler 或 Runtime 代码发布版本分别表达.

理由: 同一规则的新版本可能改变证据排除条件. 审计须能解释原决定当时采用哪套语义; 升级不得改写已保存的决定或命令结果.
具体规则版本表示、登记存储、旧版本退役、契约内容保留及原子核验实现尚待设计.

### Q75: 普通规则退役不自动撤销既有处置

普通规则版本退役只阻止该版本的新提交, 不自动撤销此前已接受处置的效力.
旧处置继续遵守已确认的证据范围、适用条件和显式取代关系; 退役本身不改变 Intent 当前判断或推进 Judgment Revision.
新证据及真实资格条件变化仍按原规则重新判断.

若发现规则缺陷而需要撤销既有处置, 须通过明确、可审计的操作改变当前判断并推进 Judgment Revision.
旧决定、原命令与原结果保留, 原命令重投仍按当前读取权限返回原结果. 已提交 Outcome 保持不可改写.

理由: 日常版本升级不应使所有未终结 Intent 自动改变判断. 普通退役与撤销既有处置须分别表达;
具体撤销命令、资格、范围、并发和审计协议留待下一轮设计. 规则登记存储与治理仍未实现.

### Q76: 撤销当前处置不恢复更早处置

撤销仅移除明确范围内的当前处置, 该范围重新等待判断; 不自动恢复更早被取代的采用或排除结论.
依据原始证据重新确定必要的阻塞, 范围外的处置继续遵守原适用条件. 若希望再次采用旧结论, 须提交新的合格决定.

撤销本身不生成 Outcome 或危险重试许可. 原始报告、旧决定、取代/撤销历史及原命令结果保留; 已有 Outcome 不可改写. 依 Q75,
改变当前判断的撤销须明确审计并推进 Judgment Revision.

理由: 撤销有缺陷的新处置, 不表示更早的结论在当前上下文仍然成立. 自动恢复可能未经重新审查就重新排除真实证据或解除冲突.
本轮确认撤销后的判断语义; 撤销命令的身份、权限、依据、范围表示和并发协议仍待细化.

## 序列化研究依据

- [Erlang binary_to_term 与 term_to_binary](https://www.erlang.org/doc/apps/erts/erlang.html): safe 不替代应用验证,
  deterministic 不承诺跨 OTP major 字节稳定.
- [ETF 规范](https://www.erlang.org/doc/apps/erts/erl_ext_dist.html): 可编码运行时对象不等于保存其恢复语义.
- [Ecto.Schema map 类型](https://hexdocs.pm/ecto/Ecto.Schema.html#module-the-map-type): 逻辑映射受 Adapter 与 codec
  影响.
- [Ecto SQLite3 Adapter](https://hexdocs.pm/ecto_sqlite3/Ecto.Adapters.SQLite3.html):
  实际支持与配置需按项目锁定版本核查.
- [PostgreSQL JSON Types](https://www.postgresql.org/docs/current/datatype-json.html): JSONB 不保存所有表示细节,
  并有数值与文本限制.

以上是设计依据, 不是项目依赖版本或实现 round-trip 验证的证明.

## lease 时间研究依据

- [Erlang Time and Time Correction](https://www.erlang.org/doc/apps/erts/time_correction.html): 实例内 monotonic
  与可跳变的 system time 不同, 不直接比较不同 Worker 的裸 monotonic expiry.
- [PostgreSQL 时间函数](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT):
  now/transaction_timestamp 是事务起点, clock_timestamp 与之不同.
- [SQLite 日期时间](https://www.sqlite.org/lang_datefunc.html) 与 [VFS](https://www.sqlite.org/vfs.html): now 来自当前
  VFS, 一致性限于同一 sqlite3_step, 不等同 PostgreSQL 事务时间.

以上支持时间边界分析, 不证明部署时钟一致或 lease 协议正确; 时间跳变不能作为旧 Worker 停止或危险重试的依据.
