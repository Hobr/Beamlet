# 按依赖组织的实现路线

本路线描述首版的开发顺序与验收条件. 范围见 [首版范围](first-release-scope.md), 组件边界见
[整体架构](runtime-architecture.md).

## 1. 依赖顺序

```mermaid
flowchart LR
    D0["0: 契约与实现前选择"] --> D1["1: 领域规则与值"]
    D1 --> D2["2: Storage"]
    D2 --> D3["3: 本地执行闭环"]
    D3 --> D4["4: 远端 Worker"]
    D3 --> D5["5: Pending 与恢复"]
    D4 --> D6["6: 调用方组合与首版验收"]
    D5 --> D6
```

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| 0. 契约与选择 | 公开领域类型与错误分类, 后端/驱动与协议选择, 资源绑定和 History 编码方案 | 接口对应 SPEC; 未决项有明确边界, 不使用任意 term 或内存缓存作为持久权威 |
| 1. 领域规则与受限值 | IEO, 资格/证据/停止规则, 定义相等与值域验证, History 逻辑材料 | 无 Repo/网络/进程依赖; 原子接受, Unknown/旧成功阻塞等场景对应代码测试; 数值/Unicode/预算边界可测 |
| 2. Storage 与后端符合性 | 原子命令, 一致读取, 物理约束与 History 映射; SQLite/PostgreSQL Adapter | 两个真实后端分别通过提交/领取/授权/报告/终结竞争, 回滚, 响应丢失重投, 保护内取时 |
| 3. 本地执行闭环 | Coordinator, 持久扫描, Worker 会话, 同步示例 Handler, 查询/结果复用入口 | 完整 Submit 到 ReadFacts 路径; 通知全丢仍发现工作, 重启不重复旧调用; Unknown 不能由超时变 Failed |
| 4. 跨设备执行 | 选定 Transport 的版本化消息, 可信身份, 重连/路由, 环境匹配与资源约束 | 两种部署形态验证; 错 scope/旧会话拒绝; 授权回复/报告丢失恢复; 设备资源不能被同名替换; 未获许可的分区 Worker 不新调用 |
| 5. Pending 与恢复 | 持久完成关联, 回调 Adapter/发送者保留或 inbox, 能力查询和安全重试 | 完成先于 Pending, 原 Worker 丢失后完成; 验签/账户/重复/冲突测试; 原幂等窗口和旧协议不能被升级延长/改义 |
| 6. 调用方组合与交付 | 稳定提交与事实读取便利层, 多 Agent/Tool Call 验收, 部署与兼容性说明 | 原依赖清单恢复部分结果/汇总; 两 Intent 隔离与共享 Worker 重启; 两后端完整验收, 旧数据读取和明确未支持边界 |

一个 SQL 后端可先用于打通闭环, 另一个随后接入; 正式宣称双后端支持前, 两者都须达到阶段 2/6 的符合性要求.
阶段 4 与 5 可以并行, 但共享消息/绑定接口须先收敛.
LLM, 文件, Browser/Device 的支持分别取决于其版本化 Operation/Adapter 验收.

## 2. 实现前的选择

- API/Behaviour 的最小签名, principal/权限上下文和错误分类, 同步等待超时的返回形式.
  语义义务见 [存储接口](storage-command-contracts.md).
- 首个 Transport, 可信身份映射, 协议/codec 版本协商, 连接限制与应用重投; 不强制 Distributed Erlang.
- Ecto/驱动/数据库版本, 事务隔离/锁形式与持久性配置; SQLite 不跨设备共享文件.
- History 的记录身份, 提交组/次序表示与字段预算, 非复用/耗尽行为及分页权限.
- Worker incarnation 编码, 资源身份/权限验证与 Handler 登记配置.
- 首批示例 Operation 的外部协议: 至少一类同步操作与一类 Pending 操作.
  参见 [Operation 样例](operation-handler-contracts.md).

动态成员注册, 全局调度公平性, 人工协调, 规则治理, Authority 迁移和归档属于后置能力.
初期可采用简单的进程树, 连接池和扫描策略, 但单进程部署不能替代数据库并发约束.

## 3. 验收方法

1. 将 SPEC 的行为与不变量对应到领域纯规则和代码测试; Quint 的观察快照不直接成为产品 schema.
2. 分别用真实 SQLite/PostgreSQL 的竞争与故障注入检验原子性, 持久性, 重投及时间采样.
3. 检验 Transport/Handler 的可信来源, 资源绑定, 外部幂等窗口和完成证据, 记录依赖版本与部署条件.
4. 用多 Worker/Agent 场景验证作用域隔离, 用调用方持久清单验证重启后的依赖恢复与结果复用.
5. 若实现与规格不一致, 先判断实现错误, 规格遗漏或抽象边界, 再修正相应规则和回归场景.

抽象模型提供的证据与尚未验证的前提见 [模型边界](../quint/README.md#模型边界).
