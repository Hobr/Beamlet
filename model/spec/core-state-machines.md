# SPEC: 核心状态机与结果接受

本文规定 Intent、Execution、Outcome 的状态、证据与接受守卫。首版对无法安全解决的 Unknown/冲突保持 Open 并提供事实读取。
协调/治理章节保留后置能力的约束，交付边界见 [首版范围](first-release-scope.md)。
首版逻辑接口和具体选择由 [原子存储命令](storage-command-contracts.md)、[持久值与消息](persistent-values-and-messages.md)
及 [Handler/恢复策略](handler-recovery-contracts.md) 细化；物理字段、数据库映射和特殊协议仍需实现设计。

相关文档: [领域语言](../../GLOSSARY.md), [RFC 0001](../rfc/0001-core-boundaries.md).

## 1. 范围与假设

- 核心处理独立 Effect 的提交、执行尝试、权威结果接受与恢复事实, 不恢复调用栈或 Agent 控制流.
- 每个 Intent 有唯一逻辑 Authority. 多 Coordinator 可以在同一权威存储规则下处理请求; 第一阶段不允许双边权威提交.
- Worker 必须遵守启动授权协议. 本文不证明不合作或恶意 Worker 不会直接调用外部服务.
- 数据库事务不包含真实外部执行, 外部系统也不默认提供幂等、查询、取消或 fencing.
- 第一阶段正式支持 Ecto SQLite 与 PostgreSQL, 不实现独立 Memory/ETS Storage.
  具体故障与掉电保证、存储配置和复制保证尚未定义.
- 涉及组合状态的不变量以一致的已提交权威状态为对象, 不以分别读取的瞬时结果为对象.

## 2. Intent

| 状态 | 定义 |
|---|---|
| Open | 没有 Outcome, 逻辑操作尚未终结 |
| Closed | 已有不可变 Outcome, 逻辑操作已终结 |

合法终结转换为 Open -> Closed, 必须与 Outcome 和终结历史共同提交. 不允许 Closed -> Open 或替换已有 Outcome.
需要新的逻辑操作时建立新的 Intent.

Closed 不意味着所有外部操作已停止, 也不禁止保存迟到报告. Ready、Running、Waiting 和 NeedsReconciliation 等操作视图不是
Intent 生命周期状态; 调度所需事实和投影仍待定义.

## 3. Execution

### 3.1 协议状态

| 状态 | 定义 |
|---|---|
| Prepared | 尝试已建立, 尚未授予启动许可 |
| StartAuthorized | 启动许可已持久化, 外部操作可能已开始 |
| Waiting | 已接受可恢复的等待登记, 不依赖常驻 Worker |
| Unknown | 已存在可能执行的依据, 当前证据不足以可靠继续处理 |
| Resolved | 已接受足以判断尝试结果的证据, 不一定被采用为 Outcome |

StartAuthorized 不是 Running 的同义词. Resolved 不表示报告绝对真实或未来不会有矛盾; 已知冲突必须阻止未经协调的自动终结.

### 3.2 已确认的主路径

| 转换 | 触发与最低守卫 |
|---|---|
| Prepared -> StartAuthorized | Intent Open, Execution 当前合格, Worker 临时权限有效, 启动许可持久化并绑定 incarnation |
| StartAuthorized -> Waiting | 接受 Handler 契约支持的有效 Pending 登记及可恢复关联 |
| StartAuthorized / Waiting -> Resolved | 接受可验证的确定结果或协调证据 |
| StartAuthorized / Waiting -> Unknown | 发现需要协调的不确定性, 不据此自动重试或终结 |
| Unknown -> Waiting | 新证据恢复合法等待关系 |
| Unknown -> Resolved | 新证据足以判断此次尝试结果 |

表列主路径不是已经完成的全部转换规范. 不得从表中缺省推断其他转换合法;
启动前结束、报告冲突、特殊协调与乱序消息的状态投影仍待补充.

### 3.3 资格与 lease

- 生命周期与直接成为 Outcome 候选的资格正交. 撤权不伪造尝试结束, 不阻止保存证据.
- 从未启动但已撤权的尝试可以保留为 Prepared; 不要求为归档它伪造完成结果.
- 同一 Intent 第一阶段默认最多一个当前被授权执行的尝试, 不提供主动 hedging. Intent 使用可为空的 current_execution_id
  表达当前关联; 正常完成还须满足 Open、来源、证据等守卫.
- 替代尝试时原子建立新 Execution 并切换当前关联. 旧尝试不直接赢得 Outcome, 但保留真实进展和报告.
- 已撤权的尝试不能直接赢得 Outcome, 即使它报告成功且 Intent 仍 Open. Authority 可以按明确的 reconciliation
  流程验证使用其证据.
- Worker lease 到期不自动撤销 Execution 的结果接受资格. Authority 可以接受未撤权尝试的合格迟到结果.
- 到期撤除相应临时控制权限; 已授权而无可靠结果或等待登记时可标 Unknown, 保留当前尝试资格. 先协调, 满足安全条件后才替代,
  不立即重新执行.
- Waiting 不依赖常驻 Worker, Worker lease 到期本身不能将其判为 Unknown.
- 替代尝试的授权必须明确处理旧资格并验证安全重试条件. lease 的 Authority 时间、generation、失效及重启原则见
  [lease 与权限 SPEC](leases-and-permissions.md); 具体存储和请求去重仍待定.

## 4. 启动、派发和恢复

- Worker 调用可能产生副作用的 Handler 前必须取得已持久化的 Start Authorization.
- Start Authorization 绑定可序列化的 Worker incarnation. 重启产生新 incarnation, 不能直接继承旧许可重新调用.
- 授权已提交而外部调用尚未发生时崩溃也可能产生保守 Unknown; 没有 Running 报告不能证明未执行.
- 派发重投保留同一 Execution 身份; 报告重投只重投证据; 外部重新执行属于新的安全决策. 三者不得混同.
- 同一 Execution ID 不是外部幂等保证. 启动请求的 token 身份、原许可回复与领取重投规则见首版存储命令契约.
- 未授权启动的 Prepared 可以重新投递; Authority 原子确认从未授予启动许可且旧领取资格失效后, 可让新 Worker 领取同一
  Execution.
- 已授予许可则新 incarnation 不接续旧许可调用 Handler. 再次执行须建立安全的新尝试; 不依据 Worker
  声称未收到许可或未执行判断.
- 待处理工作必须能从持久事实重新发现. 调度唤醒与 Outcome 通知用于降低延迟, 不是唯一恢复依据.

## 5. 报告与冲突

- 可接受的报告必须验证身份、来源和操作契约. 具体身份、编码、认证和大小限制待定.
- Durable 模式不得在报告证据落盘前确认已持久化.
- 已持久化、Outcome 已接受、未采用/待协调是不同含义; 一次响应可同时携带多个已成立的含义.
- 已撤权报告可以保存后确认未采用, 不要求发送方必须赢得 Outcome 才能停止重投.
- 重复报告可以去重, 矛盾报告不得覆盖或按最后写入/时间戳选择结果.
- 已知冲突且尚无 Outcome 时, 阻止未经协调的自动终结. 已有 Outcome 时保留冲突, 不改写结果.
- Q61: 未协调冲突独立于生命周期持久化. 冲突报告保留最近一次有依据的生命周期投影, 不按最后报告回退或改判; Resolved
  可以同时存在未协调冲突. lease 等独立协议转换仍按自己的守卫执行.
- 解除冲突须明确 reconciliation, 不覆盖原始证据, 不以新报告自动清除争议. 显式 Cancelled 仍遵守原有控制面规则.
- 协议不能预知未来报告. 报告确认前 Worker 崩溃且未保存自身证据时, 仍可能 Unknown.

## 6. Outcome

### 6.1 分类与来源

| 分类 | 定义 |
|---|---|
| Succeeded | 接受操作契约定义的正常完成结果, 不要求业务结果正面 |
| Failed | 接受明确错误, 或依据已知事实与策略决定无法正常完成 |
| Cancelled | 接受停止继续处理 Intent 的逻辑决定, 不证明外部停止或回滚 |

Unknown、超时和预算耗尽本身不是终态 Outcome. 审批拒绝等业务结果可按契约作为正常完成数据.

Outcome 属于 Intent. 普通 Handler 完成保留 Execution 关联; 未执行就取消、Authority 策略终结等不需要虚构 Execution. 每个
Outcome 均应有明确来源、理由及必要证据关联; 不允许无依据成功.

### 6.2 接受守卫

任何终结必须验证 Intent Open、来源和资格有效, 并满足对应操作契约或控制面权限. 已知未协调冲突阻止自动终结.

Failed 至少还要求:

1. 明确的错误或终结依据.
2. 策略决定不再尝试.
3. 没有未解决且仍可能改变逻辑结果的不确定性.

Q62: 旧非当前/已撤权尝试的成功证据尚未协调时, 当前尝试已知失败也不能普通提交 Failed. 必须按 Operation
契约明确采用或排除旧成功证据; 旧成功不能直接抢占 Outcome, 也不能因失去资格而被忽略. 提交原则见 6.4; 命令身份原则见 Q66;
具体身份表示、证据处置字段与并发协议待定.

Failed 不证明不存在部分外部副作用. Cancelled 可以终结未解决 Intent, 但不将未知外部事实改写为已知失败或已停止.

取消和合格完成竞争时, 第一个通过全部验证并完成权威事务提交的决定获胜. 不按 Worker 时间戳倒推优先级,
不允许取消请求天然覆盖已提交成功.

### 6.3 原子终结

- Outcome、Intent Closed 与对应终结历史必须在一次本地事务共同提交.
- 普通合格完成默认同事务保存报告、更新 Execution、插入 Outcome、关闭 Intent 和写历史.
- 已撤权、冲突或待协调报告可以仅持久化证据而不终结 Intent.
- 存在 Outcome 后任何新候选都不能产生第二个 Outcome. 迟到事实仍可保存.

模型对应: [正常闭环入口](../quint/beamletNormalUse.qnt) 用显式停止/重试策略区分失败事实与终结资格;
已具备停止依据的合格失败同一步保存报告、Execution、Outcome/Closed 和 History.
核心原语仍保留先存失败事实、后作停止决定的处理上下文. 首版最小策略的额度、提前停止与错误分类边界见
[Handler/恢复契约](handler-recovery-contracts.md); 不扩展为通用策略治理算法.

### 6.4 证据协调命令（后置）

以下约束用于未来的协调/治理能力。首版没有人工采用/排除接口，证据不足时保持 Open。

Q63: 协调决定引用具体报告、Operation 契约依据、理由及处理主体, 明确采用的结果和排除的证据对本次判断的影响. 原始 Report
不覆盖, 不以永久“已协调”标志代表所有证据已经处理.

Authority 在同一 Intent 原子边界重验当前证据和资格, 保存协调 History, 再解除对应阻塞或提交 Outcome. 新证据须重新判断,
不能由旧处置自动涵盖. 审查过期按 Q70 判断版本校验; 判断作用域、具体相关变化清单与 SQL 表示仍待细化.

Q64: 可由明确登记且条件可验证的 Operation 规则自动提出协调, 也可由获授权主体显式提出.
缺少适用规则或证据不足则保持待协调. 两类入口都遵守相同证据、资格、原子提交和审计规则, 不允许改写已有 Outcome.

Q65: 人工决定的审查上下文在提交前已过期时拒绝并返回当前上下文, 不静默改写决定.
自动规则可以对新上下文重新求值并提出新的可审计决定. 普通心跳不属于影响判断的证据/资格变化.

Q66: 每个协调命令具有 Intent 范围内稳定 ID. 原子提交须保存命令身份、领域内容与原处理结果, 并与决定及其 History 一致. 同
ID 同内容的重投返回原结果, 不重执行、不新增同一决定审计; 同 ID 不同内容拒绝. 已提交命令即使原快照已过期或 Intent 已
Closed, 也能被识别为重投, 不按新命令重新作资格判定. 这不会让旧决定处理新证据.

Q67: 经过权限和格式校验后的明确领域拒绝也原子保存命令身份、请求内容、当时拒绝结果和审计. 重投复用原拒绝, 不重新判断;
重新审查须用新 ID. 拒绝不制造证据处置决定或 Outcome. 通信故障、未提交的数据库异常及入域前校验失败不伪装成已提交领域结果.

Q68: 新决定与原结果读取使用各自当前权限. 已失去提交权限但仍可读取时, 重投返回原结果; 失去读取权限后拒绝返回内容,
保留原命令身份与结果, 不重新执行.

Q69: Intent 仍被保留时, 已处理命令的身份、相等性所需信息及原结果持续保留, 不默认 TTL 清除; Closed 也适用.
归档或清理须保证旧 ID 不重新可执行, 并定义原结果查询能力.

Q70: 协调命令携带审查时判断版本, Authority 在同一 Intent 原子边界比较当前版本后重验决定. 相关持久变化递增版本;
心跳、重投和纯拒绝审计不递增. 版本相同仍须验证具体报告、契约依据和当前权限. 已处理命令的重投先识别原结果,
不重新校验为新决定.

判断版本保护新决定的提交时刻. 已接受处置的后续适用范围按其证据和资格依据判断, 不因该决定自己的版本递增而立即失效.

Q71: 冲突协调须显式覆盖本次判断相关的全部冲突报告, 逐项说明采用/排除及契约依据. Authority 原子保存处置、解除对应阻塞,
条件满足时提交成功或失败 Outcome. 原始报告、冲突历史保留; 新证据重新判断.
历史上发生过矛盾与当前是否仍有未解除阻塞分别表达, 不靠清除历史标志假装未发生冲突.

Q72: 具备逐项契约排除依据时, 可以排除全部相关矛盾报告并完成这组冲突的审查处置, 但本次结果判断仍未知, Intent 保持 Open.
不因此生成成功/失败 Outcome, 不把未知改写成未执行, 不自动授权重试. 已授权未知尝试的风险仍须独立排除;
原报告、历史冲突、命令原结果与审计保留. 新证据须重新判断.

Q73: 新决定改变先前证据处置时, 引用被取代的旧处置及对应范围. Authority 原子重验版本、引用、证据、契约与权限,
保存新决定、取代关系和审计并更新当前适用关系. 只取代明确范围, 不隐式覆盖范围外的处置;
旧决定、原始报告与命令原结果继续保留. 被取代决定的原命令重投仍返回原处理结果, 不重执行或返回最新 Outcome.

Q74: 自动决定绑定具体规则身份和语义版本. Authority 原子核验该确切版本仍被登记且条件满足, 不默认最新版本或静默迁移旧请求.
历史决定按当时版本解释, 原命令重投按当前读取权限返回原结果; 新求值形成指定规则版本、当前上下文及新命令身份的新决定.
语义版本与代码发布版本分别表达.

Q75: 普通规则版本退役只阻止新提交, 不自动撤销已接受处置, 不单独改变当前判断或推进 Judgment Revision.
旧处置仍受证据范围、实际适用条件和显式取代关系约束. 需要撤销既有处置时,
使用明确、可审计的操作改变当前判断并推进判断版本; 旧决定、原命令结果与已有 Outcome 保留.
规则登记和撤销的具体工程协议仍待细化.

Q76: 撤销只移除明确范围的当前处置, 不恢复更早被取代处置. 该范围重新等待判断, 按原始证据重新确定必要阻塞;
范围外的处置保留. 再次采用旧结论须形成新的合格决定. 撤销自身不产生 Outcome 或危险重试许可, 历史与原命令结果保留, 已有
Outcome 不改写. 明确撤销改变当前判断并推进判断版本; 具体命令字段和工程协议仍待细化.

Q77: 撤销作为独立领域操作复用协调命令的同一 Intent 身份域. 新撤销携带新命令身份、明确目标/范围与当前审查版本,
首次接受原子保存关系、命令原结果、审计及版本变化. 已处理同身份同内容请求按当前读取权限返回原成功/领域拒绝结果,
不重新执行或转向后来建立的处置; 同身份不同内容 (包括协调与撤销互换、改变范围) 冲突拒绝.
已知身份查找先于首次提交资格/审查核验, 不因新证据、Closed 或规则/权限变化改写原结果.

Q78: 普通协调权限不自动包含撤销权限. Authority 首次接受撤销时独立核验主体对具体目标/范围的授权,
再检查依据与审查版本. 自动规则须明确允许撤销且条件合格; 原命令结果读取仍只按当前读取权限判断.
两类权限可授予同一主体, 不要求新角色框架, 不赋予修改历史或已有 Outcome 的能力.
撤销专属授权尚无 Quint 区分场景或真实鉴权实现。

具体相关变化清单、权限策略、身份绑定、决定身份与关系表示、规则语义版本表示/登记/退役与历史解释材料保留、条件核验、相等性编码、归档/清理与鉴权原子协议尚待设计.
自动规则声明不是证明, 人工决定也不等同于任意状态修改. 第一阶段不引入通用协调 Workflow.

## 7. 必须保持的 Safety 性质

| 标识 | 性质 |
|---|---|
| S1 | 每个 Intent 至多一个 Outcome |
| S2 | Intent Closed 当且仅当存在 Outcome |
| S3 | Outcome 一旦提交不可替换或修改 |
| S4 | Closed Intent 不再授予新尝试或启动许可 |
| S5 | 已明确撤权的 Execution 不直接赢得 Outcome |
| S6 | 启动许可先于合规 Worker 的外部执行, 且绑定 incarnation |
| S7 | 同一 Intent 默认最多一个当前被授权执行的尝试 |
| S8 | Unknown、失联、超时和预算耗尽不单独授权危险重试或失败终结 |
| S9 | 权威终结与终结历史原子一致 |
| S10 | Durable 已持久化确认不先于证据持久化 |
| S11 | 证据处置的取代只影响明确范围, 旧决定和命令原结果保留 |
| S12 | 普通规则退役不自动改变既有处置、当前判断版本或命令原结果 |
| S13 | 撤销只移除指定范围当前处置, 不自动恢复旧结论、生成终结或危险重试许可 |
| S14 | 协调与撤销共用命令身份域; 撤销重投不执行新操作、不转向新处置, 原成功/拒绝结果保留 |

S6 是 Worker 合规与授权协议的性质, 不是数据库独自保证的外部副作用性质. S7 不是物理外部执行互斥.
报告存储、协调权限、历史粒度和具体约束仍需后续 SPEC 完整化.

## 8. 最低故障测试场景

1. 两个合格终结同时竞争: 最多一个 Outcome, 不产生 Closed 无 Outcome 的提交状态.
2. 取消与成功竞争: 验证过且先提交者获胜, 迟到事实可保存.
3. 旧尝试撤权后成功: 证据可持久化, 不直接生成 Outcome.
4. 启动授权后、外部调用前崩溃: 不推断未执行, 危险重试被阻止.
5. Worker 重启后收到旧派发/旧许可: 不直接重新调用 Handler.
6. 已登记 Human Approval, 所有进程退出: 恢复关联, 不重复创建审批.
7. Waiting Worker lease 到期: 不仅因到期转为 Unknown 或创建替代尝试.
8. Outcome 提交后通知丢失: 可查询并复用结果, 不再次执行.
9. 报告确认丢失后重投: 不导致外部重新执行或重复 Outcome.
10. 矛盾报告: 已知冲突阻止未协调自动终结; 已有 Outcome 不改写.
11. 预算耗尽且操作未知: 不自动 Failed.
12. Prepared 派发确认丢失: 重投保留 Execution 身份并重新验证启动资格.
13. Resolved 后收到矛盾报告: 生命周期投影保留, 冲突独立保存并阻止自动采用, 已有 Outcome 不改写.
14. 旧成功与当前失败无论以何顺序保存: 未协调旧成功阻止普通 Failed, 显式 Cancelled 仍可接受.
15. 协调采用旧成功: 保存具体决定、原始报告和审计, 与合格 Outcome 共同原子提交.
16. 以契约依据排除旧成功对本次判断的影响: 保留原始成功事实, 不改写尝试结果.
17. 新报告或当前资格改变后旧协调请求到达: 重新验证, 不自动沿用旧结论.
18. 未授权主体、未登记规则或条件不符: 不接受协调决定; 没有自动规则时仍可提交合格人工决定.
19. 人工审查后到达新证据: 拒绝过期请求并返回当前上下文, 不静默更新批准内容; 普通心跳不使审查过期.
20. 协调响应丢失后重投: 即使 Coordinator 重启、有新证据或 Intent 已 Closed, 已提交命令仍返回原处理结果, 不重执行决定.
21. 同一命令 ID 不同内容竞争: 首个合格原子提交确定该身份的请求与结果, 后续冲突拒绝.
22. 自动规则针对新上下文重新求值: 以新身份提交新的决定, 原请求与原结果保留.
23. 领域拒绝响应丢失或重启: 原身份、内容及当时结果保留, 重投不因条件改善而执行旧请求.
24. 被拒绝的命令改用新 ID 重新判断: 原拒绝仍保留; 同一原 ID 不同内容则冲突拒绝.
25. 提交权限撤销但仍可读取: 返回原成功或拒绝结果; 读取权限撤销后拒绝返回内容, 保留身份.
26. 入域前权限校验失败: 不占用领域命令身份, 不制造协调决定、领域拒绝结果或 Outcome.
27. 两项决定基于同一判断版本并发在途: 第一项相关处置提交后, 第二项即使未收到新报告也须重新审查.
28. 普通心跳、纯拒绝审计、原命令重投和 Coordinator 重启: 不递增判断版本或使原结果重新执行.
29. 处置自己的版本递增: 不立即撤销其刚接受的作用; 新证据或资格变化仍须重新判断.
30. 判断版本相同但契约条件或权限不合格: 不能提交新决定.
31. 冲突决定遗漏相关矛盾报告或未说明某项处置依据: 不解除阻塞或终结.
32. 完整合格冲突处置: 原子保存决定、解除对应阻塞及条件满足时的 Outcome, 原报告和冲突历史保留.
33. 新报告到达后重投原冲突处置: 返回原处理结果, 不把旧处置扩展到新证据.
34. 全部报告有明确契约排除依据: 可以完成冲突审查, 当前判断仍未知、Intent Open, 未知风险继续阻止失败终结.
35. 全部排除命令重投或以后出现新证据/终结: 返回原非终结处理结果, 不重执行或替换为最新 Outcome.
36. 全部排除前后重新作出合格明确处置: 新版审查不回退使用旧的采用记录, 原报告、命令与审计保留.
37. 新决定遗漏取代引用、引用不存在/自身/已经被取代的范围或越界: 不隐式覆盖旧判断.
38. 只取代旧决定的部分范围: 范围外的当前适用关系保留; 后续整组取代须识别各范围的当前来源.
39. 被取代决定的原命令重投, 包括 Closed 后: 返回原结果, 不重新执行决定或覆盖当前处置.
40. 并发取代或审查后新证据到达: 过期请求拒绝, 不静默重新指定引用; 同命令 ID 改变引用仍属内容冲突.
41. 规则多个语义版本并存: 按请求指定版本校验登记和条件, 不借用其他版本的条件或默认为最新版本.
42. 审查版本未变但规则版本已退役: 新提交重验登记, 不静默迁移或接受已退役版本.
43. 已处理命令对应版本退役或登记变化: 原命令按读取权限返回原成功/拒绝结果, 包括 Closed 后, 不改写旧决定或按新版本重执行.
44. 自动重新求值: 显式选定新规则版本、当前证据上下文与新命令 ID; 仅更换版本也属于领域请求内容变化.
45. 已接受非终结处置后普通退役: 保持原适用关系和判断版本, 合格后续终结仍可使用原处置; 同版本新提交拒绝.
46. 退役后新证据或合格显式取代: 仍按原证据范围与判断版本规则处理, 不把退役保护误当作永久处置.
47. 需要撤销有缺陷规则的既有处置: 明确审计并改变当前判断, 不删除历史、改写原命令结果或撤回已提交 Outcome;
    具体操作协议待定.
48. D0 被 D1 取代后撤销 D1: 指定范围无当前处置, 不恢复 D0; 原证据重新产生必要阻塞.
49. 撤销仅涉及当前处置部分范围: 其他绑定保留; 再次采用旧结论使用新合格决定, 原命令重投仍返回原结果.
50. 撤销自身与后续独立终结/新判断分开: 不把撤销解释成失败/成功或重试许可, 已有 Outcome 保持不可变.
51. 撤销 W 已接受, 新决定建立处置后回复丢失/重启/重投: 返回 W 原结果, 不转向新处置, 判断版本和审计不变.
52. 协调与撤销使用同一身份的两种到达顺序: 后续不同内容冲突拒绝; 明确领域拒绝也占用共同身份域.
53. 首次撤销的审查版本或依据不合格: 保存明确领域拒绝; 后来条件改善不重新执行旧身份, 重新审查使用新身份.

这些仍是完整产品的验证要求. 首个 [Quint 模型](../quint/README.md) 已运行其中的抽象场景,
包括终结竞争、旧尝试证据、重启/到期和报告重投; 具体覆盖以模型记录为准.
[正常闭环模型](../quint/beamletNormalUse.qnt) 另有独立完成关联、事实读取及持久候选发现的抽象场景;
Human Approval 具体协议、通知/扫描实现、完整产品冲突协调及真实后端尚未验证, 不能将整张清单视为实现测试通过.

## 9. Liveness 与未决事项

不承诺所有 Intent 自动得到 Outcome. 后续 liveness 必须明确依赖 Authority/存储最终可用、调度公平性、传输重投、Handler
或人工响应等假设. 不可查询且不允许重复的 Unknown 可以长期未解决.

计划迁移须保持一致切点、旧 Authority 撤权及新 Authority 合法激活; 具体协议未定义. 物理字段与约束、证据存储、Storage
原子接口、lease 时间依据、版本与序列化、报告认证、历史保留仍待完成. 首个 Quint 模型已落盘并运行有界抽样与场景,
完整协议和实现正确性尚未验证.

## 10. 已确认的存储与调度方向

- 首选 intents / executions / outcomes / reports / history 五个明确逻辑存储实体. reports 保存不可覆盖证据, history
  保存状态转换及重要决定, IEO 仍是领域主干.
- 领域规则不直接访问数据库、网络或时钟. 快照、命令及显式必要输入产生决定, 持久化路径必须防止该决定因并发状态变化而失效.
- Durable 正确性不依赖单个 Coordinator 或 GenServer; 后端事务及并发约束独立保障不变量. 不要求不同 Intent 全局串行.
- 影响同一 Intent 执行资格、结果判断或终结的命令共用原子并发边界. 接受影响判断的报告/冲突事实不能绕过协调,
  否则并发终结可能使用过期证据.
- 默认持久状态扫描与可丢失唤醒通知, 不强制 Transactional Outbox. 扫描必须能够重新发现待处理及必要恢复工作;
  扫描范围、索引、频率和公平性待定.
- Q51 已确认: 上层持久化业务恢复集合与等待关系, Runtime 默认负责已接受操作的最小派发、lease 检查及必要执行恢复.
  上层不必遍历全部 Runtime 表重建计算上下文.
- 统一调度投影字段尚未批准. 工作发现可以使用现有持久事实与索引, 仅在必要时补充字段; 候选处理通过原子领域命令,
  不以默认扫描推导必须全表遍历或新增通用 Job 模型.
- 纯领域测试无需 Memory Storage. SQL 存储测试使用真实后端, 各后端单独验证并发与故障行为,
  不将二者底层事务机制视为完全相同.
