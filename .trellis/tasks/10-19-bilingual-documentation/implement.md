## 验证

每批检查 `git diff --check`、相对链接/锚点/源码引用、语言顺序、代码示例对应的实际接口。将省略的隐藏 API 与简单内部结构在覆盖表中说明，不用机械注释计数代替审阅。

涉及 Elixir 文档属性时运行：
- `mix format --check-formatted`
- `mix compile --warnings-as-errors`
- `elixir scripts/quality/check-contracts-test.exs`
- `elixir scripts/quality/check-contracts.exs`
- 忽略文档属性与位置元数据的基线/结果 AST 对比。

各语言阶段收尾运行 `mix credo --strict --all` 与 `mix dialyzer`。对新增或改动的可执行 doctest 运行其所属测试；最终一次 `mix test --seed 631927` 检查跨应用文档属性编译及 doctest，期间如有新失败再缩小范围调查，不修改业务测试来使文档通过。Web/I18n 边界终检运行 `mix sobelow`、`mix gettext.extract --check-up-to-date`。注释插入行号后，`#:` 来源引用由 `mix gettext.extract --merge` 重生成；已核实仅来源行变化、`msgid`/`msgstr` 完全一致。

纯 Markdown 修改按质量规范检查路径、链接、示例、空白即可，不为其重复执行应用测试。先检查工具链/依赖，实际记录通过、失败、未执行和原因；数据库、named peers、物理跨机、付费模型、部署与发布打包不作为这次文档工作的新增验收。不执行文档中有外部副作用的命令来“验证”文字。

## 风险与回滚点

- 大范围注释有可能错述时序或公开内部协议：每批对照源码、调用方及测试，保持 false 可见性标记。
- 文档漂移：说明以源码、调用方与测试为依据；纠错时同步更新覆盖记录。
- 每批都有独立差异与验证检查点；失败时仅撤回本任务对应批次，不重置他人工作。
