# rex/erpc 查询可用性实验与 Elixir 生态方案评估

> 2026-10-17留存更新：用户已接受后续实现，依约清理本任务results/、experiments/及专用.gitignore。原始数据、脚本、日志、快照不再提供；以下要求和勾选是研究交付时的历史记录。保留研究结论、官方来源和独立复核摘要，不再声称原实验可从仓库复现。

## Goal

通过隔离多节点实验与一手资料，判断本项目只读查询应采用什么最小机制，让用户获得低扰动、故障不连带影响 Agent 的发现和重新附着能力，避免无证据地排除标准 RPC 或引入自定义协议。

## Background

当前发现实现使用自定义 Endpoint。已有设计对取消、过期准入、自动连接和 helper 生命周期提出严格要求；此前讨论中的 rex 排除理由和 Endpoint 生命周期耦合均需复核，不能作为预设结论。规划时的证据锚点与运行前提记录于 research/current-evidence.md；执行后实测、来源、推荐与限制见 research/report.md（独立review已PASS，见 research/quality-review.md；不授权产品变更）。

## In Scope and Requirements

- R1：区分传统 rex 协议、现代 `:rpc` 与 `:erpc` 的实际执行路径，不把不同机制的结果混为一谈。
- R2：通过隔离的真实命名节点观察正常查询、超时、调用方退出、远端阻塞、rex 暂停恢复、断线与后续连接行为；分别报告本地放弃结果与远端停止工作的语义。
- R3：验证查询故障的影响范围，包括 helper 存活、迟到回复和现有 Agent 的 PID/incarnation；不预设必须主动取消或与 authority 共享生命周期。低扰动指不改变业务状态、不把查询/客户端故障传播为 Agent 终止，不承诺零资源占用。
- R4：调研 OTP 内置能力与 Elixir 社区方案，比较适用范围、维护/版本兼容性、故障语义、依赖和实现复杂度；判断是否真的需要第三方库或自定义协议。
- R5：结论可复现、可追溯，明确当前保证、实测观察、推论及尚未验证的部分；给出最小可行推荐及需求取舍，不直接替换现有实现。
- R6：只使用本机临时节点和测试数据；不得连接真实集群、使用生产凭据、引入业务依赖或修改现有业务代码和既有任务契约。
